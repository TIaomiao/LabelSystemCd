# CMR-PIPELINE-01A：临床与数据契约

## 契约性质

本任务是影像数据进入处理流水线的工程底座。它不产生临床指标，也不代表医生已经认可任何结果。

## 临床安全要求

- 上传不完整时不能进入“可处理完成”状态；
- manifest 必须能回到本次上传任务、来源文件和 Series；
- 重复上传不能把不同检查或不同病例混成一个任务；
- 文件归组不确定时必须保留候选和待复核状态；
- 后续算法只能消费明确声明版本的 manifest；
- 上传状态、算法状态和医生复核状态必须独立。

## 身份与隐私

- 浏览器和共享 manifest 使用 opaque case/upload/series ID；
- 患者姓名、病例号、DICOM UID、地址、日志正文和绝对路径不进入 Issue、PR 或公共日志；
- 原始数据只留在受控暂存位置；
- 数据脱敏开关不能代替服务端访问控制、最小权限和最终泄漏检查。

## 必须由产品/架构负责人确认

1. 浏览器首期支持文件夹、ZIP，还是两者都支持；
2. 单任务最大文件数、总字节数和单文件大小；
3. 上传任务保留时长和取消后的清理策略；
4. 是否允许上传非 DICOM 辅助文件；
5. manifest 是否允许人工修改后重新进入处理；
6. 任务状态在页面、报告和审计记录中如何展示；
7. 真实脱敏样本的授权范围和医生验收方式。

## 医生验收关系

本 Intake 任务不要求医生判断指标数值，但需要产品/临床负责人确认：

- 检查列表能否清楚区分上传中、待处理、处理失败和可查看结果；
- 缺序列、残缺序列和待复核序列是否被明确提示；
- 用户能否看到本次处理使用的检查、序列和版本来源。

## 当前结论

技术上传成功不等于检查可用于临床分析。只有 manifest 完整、来源明确且后续算法通过各自质量门槛时，才允许进入对应功能的技术验证或医生复核。
